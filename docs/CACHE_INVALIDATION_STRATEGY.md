# Cache Invalidation Strategy

## Overview

This document outlines the cache invalidation strategy implemented in the ConfHub backend to ensure that user-specific cached data is properly cleared when users login, logout, or change accounts.

## Problem Addressed

When users logout and login again (especially with Google OAuth), cached data from the previous session could persist and be served to the new session. This creates issues where:

- User A logs out
- User B logs in with the same device/browser
- User B receives cached data belonging to User A

## Solution Implementation

### 1. Cache Invalidation on Authentication Events

Cache invalidation is now triggered on the following authentication events:

#### User Login (`/auth/login`)
- Clears all user-specific cache when a user logs in
- Ensures fresh data is loaded for the new session

#### User Logout (`/auth/logout`)
- Clears all user-specific cache when a user logs out
- Prevents cache pollution for subsequent logins

#### Admin Login (`/auth/admin/login`)
- Clears admin-specific cache on login
- Ensures proper admin data isolation

#### Admin Logout (`/auth/admin/logout`)
- Clears admin-specific cache on logout

#### Google OAuth Login (`/auth/google/callback` and `/auth/google`)
- Clears user cache after successful Google OAuth authentication
- Handles both callback and direct token-based Google login

#### User Signup (`/auth/signup`)
- Clears cache after new user creation and login
- Ensures clean cache state for new users

### 2. Cache Invalidation Patterns

The `invalidateUserCache()` method uses the following patterns to clear cache:

```typescript
const cachePatterns = [
  `api:*`,                    // All API cache (broad invalidation)
  `*${userId}*`,              // Any key containing user ID
  `user:${userId}:*`,         // User-specific cache keys
  `api:conferences:*`,        // Conference-related cache
  `api:feedbacks:*`,          // User feedback cache
  `api:users:*`,              // User data cache
];
```

### 3. Implementation Details

#### Method: `invalidateUserCache(userId: string)`

```typescript
private async invalidateUserCache(userId: string): Promise<void> {
  try {
    // Define cache patterns to invalidate
    const cachePatterns = [
      `api:*`,
      `*${userId}*`,
      `user:${userId}:*`,
      `api:conferences:*`,
      `api:feedbacks:*`,
      `api:users:*`,
    ];

    // Parallel cache invalidation
    const invalidationPromises = cachePatterns.map((pattern) =>
      this.redisCacheService
        .delByPattern(pattern)
        .catch((err) =>
          console.warn(`Failed to delete cache pattern ${pattern}:`, err),
        ),
    );

    await Promise.all(invalidationPromises);

    // Clear session-specific cache
    await this.redisCacheService.del(`session:${userId}`).catch(() => {
      // Ignore session deletion errors
    });

    console.log(`Cache invalidated for user: ${userId}`);
  } catch (error) {
    console.error('Error invalidating user cache:', error);
    throw error;
  }
}
```

#### Error Handling

- Cache invalidation errors are caught and logged but don't prevent login/logout
- Individual pattern deletion failures are logged as warnings
- Session cache deletion failures are silently ignored

#### Performance Considerations

- Cache invalidation runs in parallel using `Promise.all()`
- Non-critical failures don't block authentication flow
- Selective pattern matching to minimize unnecessary cache clearing

### 4. Integration with Cache Middleware

The cache invalidation strategy works with:

- **CacheMiddleware**: Handles HTTP request-level caching
- **CacheInterceptor**: Handles method-level caching
- **RedisCacheService**: Provides cache operations and pattern deletion

### 5. Cache Key Generation Compatibility

The invalidation patterns are designed to work with cache keys generated by:

```typescript
// From cache middleware
const keyData = {
  url,
  method: req.method,
  userId,
  userRole,
  filters: this.extractCacheableParams(req.query),
};
```

### 6. Testing Cache Invalidation

To test cache invalidation:

1. **Login Test**:
   ```bash
   # Login as User A
   curl -POST /auth/login -d '{"email":"usera@example.com","password":"password"}'
   
   # Make cached request
   curl -GET /api/conferences
   
   # Logout
   curl -POST /auth/logout
   
   # Login as User B
   curl -POST /auth/login -d '{"email":"userb@example.com","password":"password"}'
   
   # Verify fresh data (no User A cache)
   curl -GET /api/conferences
   ```

2. **Google OAuth Test**:
   ```bash
   # Login via Google OAuth
   curl -GET /auth/google
   # Complete OAuth flow...
   
   # Make cached request
   curl -GET /api/conferences
   
   # Logout and login with different Google account
   # Verify cache is cleared
   ```

## Configuration

Cache invalidation can be configured through:

- Redis connection settings
- Cache TTL values
- Invalidation pattern customization
- Error handling behavior

## Security Considerations

- Cache invalidation prevents data leakage between user sessions
- User-specific cache patterns prevent cross-user data access
- Error handling ensures authentication flow continues even if cache fails

## Conclusion

This cache invalidation strategy ensures that user-specific cached data is properly cleared during authentication events, preventing cache-related security issues and ensuring users always receive fresh, accurate data for their sessions.
